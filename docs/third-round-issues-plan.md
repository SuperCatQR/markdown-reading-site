## 3. 具体实施边界

### #59：菜单退出不等于结束查找

主要位置：`src/search-navigation.js`，参考 `src/reader-tools.js` / `src/ui.js` 已有菜单处理方式。监听器随搜索导航生命周期销毁；外部点击只关闭弹层，Escape 处理应避免继续传播而触发临时工具的返回逻辑。点击菜单内部操作不能被提前拦截，summary 原生切换与 Tab 行为保持。

### #60 / #61：一组搜索上下文，两种真实来源

主要位置：`src/directory-view.js`、`src/manuscripts.js`、`src/main.js`、`src/directory-state.js`、`src/search-navigation.js`。

- 使用现有 reader URL 参数传递完整查询、模式与类别，hash 只承担具体段落及局部高亮；不把跨段关键词的局部词当成整次查询。
- 搜索视频标题如需跨 P 选目标，在来源顺序中选择真实有正文证据的稿件；不能因 `group.parts[0]` 恰为元数据命中而丢掉其他 P 的正文上下文。元数据独占命中可进入正文并保留查询，但不创建假的段落锚点或命中导航。
- 全站来源状态显式绑定本次进入与原目录状态，由导航入口创建并验证；跨 P 与逐处导航继承该来源，不能被后续本视频查找或普通目录入口错误识别。
- 返回全站结果复用现有目录状态清洗、URL 和会话恢复。共享链接只传可分享查询，不把滚动、历史对象或敏感个人状态塞入 URL；没有原会话时明确缺省行为。
- 需要同时验证页面刷新、后退/前进、修改查询后返回、标签与排序、分批加载、展开段落、存储禁用、旧状态污染，以及局部工具进度保护。

### #62：先验证收益，避免只是换一种全库下载

当前 `scripts/reader-content.js` 从已校验正文派生 `{id,text}` 块，`src/search-loader.js` 下载、解析并归一化全部选定类别，`src/search.js` 逐块精确匹配。已有 BVID 分片可作为候选正文获取的基础。

本地 Node 可行性原型（同一 583 篇数据、同一 `gzipSync` 设置）结果：

| 表示 | 解码字节 | 本地 gzip 字节 | 结论 |
| --- | ---: | ---: | --- |
| 当前全库对象 | 16,446,017 | 5,762,969 | 比较基线；本地 gzip 与线上编码大小不同 |
| `[id,text]` 元组 | 16,156,925 | 5,738,846 | gzip 仅减少约 0.42%，不值得独立换格式 |
| 完整字符对→稿件倒排表 | 11,581,543 | 3,569,667 | 自身仍大，还需正文；“海德格尔”候选正文约 1.99MB gzip，总量已接近基线 |
| 每稿件 1KB 固定位签名（JSON/base64） | 830,230 | 574,960 | 较小但误报较多；“海德格尔”候选 238 篇/223 视频，正文约 3.58MB gzip |
| 每稿件 2KB 固定位签名（JSON/base64） | 1,625,442 | 1,105,685 | 误报更少；“海德格尔”候选 179 篇/169 视频，正文约 2.90MB gzip |

上述候选方案在“海德格尔、胡塞尔、何为无意识、审美 痛苦、的”五个样例里未出现正文漏检，但这不是完整正确性证明。字对签名有误报，必须正文复核；单字无法按该签名缩小范围，会扫描全部正文。正文大小是候选视频块合并后统一 gzip 的近似，独立请求的真实压缩、响应头、连接与并发耗时未测，不能将相加值当成线上承诺。

建议按以下门禁选型：

1. 原型采用紧凑二进制候选表示，比较固定位签名与分桶字对倒排，绑定构建内容指纹；构建候选只来自经过校验的正文，排除校验参照。
2. 候选索引用于安全排除无匹配正文，不直接输出结果；剩余正文按有界并发获取，复用现有缓存。精确复核后一次性宣布最终计数与排序，不把部分结果显示成完成。
3. 综合搜索单独保留元数据准入，并确保候选排除不隐藏元数据命中文章的正文证据；原句与跨段关键词逐篇精确验证。不支持预筛选的短词、Unicode/空白边界或广泛查询走明确完整扫描路径。
4. 比较 583 篇真实全量查询集的结果 ID、稿件类别、段落 ID、证据文本、P 顺序及分数/排序，与旧实现逐项等价。涵盖中文/西文、大小写、空白、标点、组合字符、emoji、单字、高频词、未命中、跨段关键词和仅元数据命中。
5. 浏览器正常与 150ms/1Mbps 条件各至少 3 组冷、热样本，记录整个请求集合的传输/解码字节、下载、解析、归一化、计算、DOM、输入到结果可用时间及内存。区分首屏资源与搜索新增资源，并给出测量工具与内存指标局限。
6. 选用真实端到端更优、最差情况可控的方案。常用概念查询争取冷下载量至少减少约 30%，该数值是试验目标；若多请求延迟抵消收益，调整聚合分片/候选表示后复测，而非只报告索引文件变小。Worker 可改善主线程响应，但不能单独声称解决下载量问题。

不增加运行时后端、不默认改为仅标题、不绕过快照校验，也不把付费服务或新依赖作为前置条件。

### #63：紧凑但仍可辨认、恢复和管理

主要位置：`src/reading-history-browser.js`、`src/followup-reading.css`，实施时同步设计说明。两行仅为最近阅读标题的默认视觉预览；原始完整文本仍在 DOM/辅助技术名称中，并提供可操作的展开查看入口，不能仅依赖 hover/title。继续按钮无需先展开，管理区不复制不必要的主操作；更新、撤回、存储失败说明仍可读。

验证长/短/超长标题、0/1/20 条记录、异常状态、320/390/1440px、深浅主题、200% 放大和键盘。以“最近阅读区高度”和“首条目录标题进入视口的位置”比较，正常 390px 默认状态争取降至约 150px 内、首条标题前移至少约 50px；带错误说明时不强行套用高度指标。原版本和段落恢复逻辑保持。

## 4. 执行顺序与交付

1. **交互批次：#59 → #60 + #61。** 菜单退出独立提交；搜索入口与返回来源一起设计，在同一独立分支按可审阅提交拆分。先补真实浏览器复现及上下文/历史回归，再修复。
2. **展示批次：#63。** 可与上一批独立推进，保留直接继续，交付前后布局数据及截图。
3. **性能批次：#62。** 先交付基准与候选索引原型评估，再实现选定方案。性能任务范围较大，单独提交/PR，避免与交互修复混合审阅。
4. **后续契约批次：#57。** 保持维护者此前后续决定，在系列关联与上游契约明确后单独推进。

执行修复时沿用独立 worktree 与 `codex/` 分支；可复用干净、已合并的 managed worktree，但需从最新 `origin/main` 建新分支。各批次保持内容快照与依赖不变。必要时使用已获授权的子代理，按不重叠文件职责分工，root 负责统一状态协议与最终集成。

每批完成后运行相称的单元与浏览器回归、`pnpm validate`、Pages 子路径构建，并做独立代码复审。先验证关键回归能捕捉人为破坏条件，再提交。修复交付明确哪些只是本地验证、哪些通过 CI 和线上部署；本计划不提前关闭 issue 或发布实现。
